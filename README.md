# The Lenny Growth Assistant

An enterprise-grade, full-stack RAG (Retrieval-Augmented Generation) knowledge assistant that transforms 260+ episodes (8,637 dialogue chunks) from Lenny's Podcast into a grounded product and growth management assistant.

---

## 1. Project Overview

### Target Users
- **Product Managers (PMs & Senior PMs)**: Seeking battle-tested frameworks (e.g., product-market fit metrics, continuous discovery, feature prioritization) backed by experienced product leaders (Brian Chesky, Marty Cagan, Shreyas Doshi, Elena Verna).
- **Growth Leaders & Growth Engineers**: Looking for verified growth playbooks (PLG vs sales-led growth, retention loops, pricing strategy, viral loops).
- **Founders & Operators**: Requiring rapid, grounded insights on scaling organizations, hiring, leadership, and fundraising from top VCs and tech founders.

### Problem Solved
Accessing specific insights across 260+ podcast episodes (~400+ hours of audio / hundreds of thousands of lines of transcripts) presents major challenges:
1. **Keyword Search Limitations**: Standard keyword search fails to capture semantic meaning or nuanced strategic advice.
2. **Hallucination & Misinformation**: Generic LLMs hallucinate product advice or blend unverified blog posts with expert opinions.
3. **Verification & Attribution**: Operators require exact source attribution (guest name, episode title, publication date, timestamp) to trust and share insights.

### Grounded Retrieval & Source Attribution
The Lenny Growth Assistant enforces **strict vector retrieval grounding**. Every statement generated by the assistant is grounded in transcript evidence retrieved from PostgreSQL via `pgvector`. The system provides clickable source citations referencing the exact guest name, episode title, and timestamp. If the podcast archive lacks sufficient information to answer a query (vector distance $\ge 0.4$), the assistant refuses to guess and returns an exact, predictable fallback message.

## 2. Core Features

### Grounded Lenny Q&A
- **Semantic Vector Search**: Powered by PostgreSQL + `pgvector` nearest-neighbor search using 384-dimensional embeddings.
- **Strict Distance Thresholding**: Enforces a cosine distance threshold of `< 0.4`. Weakly related chunks are discarded.
- **Source Citations**: Appends structured citations `[Episode: Guest Name, Timestamp/Topic]` with YouTube time-stamped links when available.
- **Predictable Fallback**: Returns exact fallback string when no transcript chunk satisfies the similarity threshold:
  > `I do not have sufficient information in Lenny's podcast archive to answer this.`

### Ship 30 for 30 Essay Generator
- **Structured Output**: Generates ~1,250-word grounded essays adhering to the Ship 30 for 30 framework (Hook, Thesis, Short Paragraphs, Headings, Bold Anchors, Actionable Checklist).
- **Grounded Content**: Leverages `RetrievalService` grounding to pull transcript evidence while ensuring zero fabricated quotes or ungrounded claims.
- **Automatic Artifact Creation**: Automatically packages generated essays into persistent Markdown artifacts opening in the side-panel viewer.

### Artifact Engine & Sandboxed Viewer
- **Persistent Storage**: Artifacts are saved to PostgreSQL with foreign key relationships to sessions and messages.
- **Dual View Modes**: Supports toggling between Rendered View (formatted typography / HTML canvas) and Code View (raw source with one-click copy).
- **HTML Sanitization**: Backend sanitizes dangerous HTML markup using Rust Ammonia (`nh3`) bindings before persistence.
- **Iframe Isolation**: Front-end renders HTML artifacts inside an isolated `<iframe>` enforcing `sandbox="allow-scripts"` (strictly omitting `allow-same-origin` and `allow-top-navigation`).

### Provider Architecture
- **Multi-Provider Support**: Supports local Ollama (`llama3.2:3b`), Cloud OpenAI (`gpt-4o-mini`), and Anthropic Claude via official Claude Agent SDK.
- **Seamless Switching**: Users can select their preferred provider from the application header without restarting the application.

## 4. Provider Architecture

The provider layer decouples model execution from core retrieval and business logic using the `BaseLLMProvider` abstract interface and `ProviderFactory`.

```text
               BaseLLMProvider (app/providers/base.py)
                      │
     ┌────────────────┼────────────────┐
     ▼                ▼                ▼
OllamaProvider  OpenAIProvider  ClaudeProvider
 (llama3.2:3b)   (gpt-4o-mini)  (claude-agent-sdk)
```

### Provider Responsibilities
- **`BaseLLMProvider`**: Abstract base class defining `generate_stream()` and `check_health()` contracts.
- **`ProviderFactory`**: Instantiates providers dynamically based on user selection (`ollama`, `openai`, `claude`).
- **`OllamaProvider`**: Connects to local Ollama service (`http://localhost:11434`). Default model: `llama3.2:3b`.
- **`OpenAIProvider`**: Connects to OpenAI API (`gpt-4o-mini`).
- **`ClaudeProvider`**: Integrates `ClaudeSDKClient` with `claude-agent-sdk`.

## 5. RAG / Retrieval Documentation

### Retrieval Pipeline Steps
1. **Transcript Acquisition**: Official repository `ChatPRD/lennys-podcast-transcripts` containing 260+ Markdown transcripts.
2. **Metadata Extraction**: YAML frontmatter parsing (`guest`, `title`, `youtube_url`, `publish_date`).
3. **Dialogue Chunking**: 500–800 token sliding windows with 100-token overlap, preserving speaker tags and timestamps.
4. **Vector Embedding**: Embeds chunks into 384-dimensional vectors using `sentence-transformers/all-MiniLM-L6-v2`.
5. **PostgreSQL Persistence**: Stores chunks in `transcript_chunks` table indexed via HNSW (`idx_chunks_embedding_hnsw`).
6. **Vector Search**: Computes cosine distance (`<->`) against query vector.
7. **Similarity Threshold**: Applies threshold `distance < 0.4`.
8. **Grounding Context & Fallback**: If zero chunks satisfy distance `< 0.4`, returns exact fallback:
   > `I do not have sufficient information in Lenny's podcast archive to answer this.`

*Security Note*: Transcript content is treated strictly as **unprivileged source DATA** inside explicit `<transcript_data>` tags, preventing prompt-injection instructions inside transcripts from overriding system prompts.

## 6. Ingestion Documentation

The ingestion pipeline populates PostgreSQL with transcript vectors:

```bash
cd backend
$env:PYTHONPATH="backend"; .\venv\Scripts\python.exe -m scripts.ingest
```

### CLI Command Options
- `--repo-url`: Source transcript repository (default: `https://github.com/ChatPRD/lennys-podcast-transcripts`).
- `--data-dir`: Local transcript cache folder (default: `data/transcripts`).
- `--batch-size`: Vector embedding batch size (default: `32`).
- `--limit`: Optional episode count limit for dry-run testing.
- `--force`: Force re-download repository archive.

### Idempotency & Corpus Size
- **Chunk Hash**: SHA-256 hash computed over `episode_title`, `guest`, `timestamp`, `speaker`, and `chunk_text`.
- **Idempotent Storage**: Existing chunk hashes are skipped on re-ingestion, preventing duplicate records.
- **Corpus Count**: **8,637 ingested transcript chunks**.

## 7. Database Documentation

Database persistence is powered by **PostgreSQL 16 + pgvector** managed via SQLAlchemy async engine (`asyncpg`) and Alembic migrations.

### Entities & Schemas
- **`Session`** (`sessions`): `id` (UUID PK), `title`, `created_at`, `updated_at`.
- **`Message`** (`messages`): `id` (UUID PK), `session_id` (FK), `role` (`user`/`assistant`), `content`, `sources` (JSONB array), `created_at`.
- **`Artifact`** (`artifacts`): `id` (UUID PK), `message_id` (FK), `session_id` (FK), `artifact_type` (`markdown`/`html`), `title`, `content`, `created_at`.
- **`TranscriptChunk`** (`transcript_chunks`): `id` (UUID PK), `chunk_hash` (Unique String), `guest`, `episode_title`, `youtube_url`, `publish_date`, `timestamp`, `speaker`, `chunk_text`, `embedding` (`vector(384)`). Index: `idx_chunks_embedding_hnsw` (HNSW cosine).

## 10. Artifact Security Documentation

HTML artifact rendering enforces strict defense-in-depth security:

### Backend Sanitization
HTML artifacts pass through `ArtifactSanitizer` wrapping **Rust Ammonia (`nh3`)** bindings before persistence. Removes `<script>` tags, inline handlers (`onerror`, `onclick`), and `javascript:` URIs.

### Frontend Sandboxed Iframe
HTML artifacts render inside an `<iframe>` with hardcoded sandbox attributes:

```html
<iframe sandbox="allow-scripts" srcdoc="..." title="Artifact Preview" />
```

- **Included Directive**: `allow-scripts` (enables dynamic rendering and script execution inside iframe).
- **Omitted Directives**: 
  - `allow-same-origin` is **STRICTLY OMITTED** (assigns an opaque origin, preventing access to parent `document.cookie`, `localStorage`, or session tokens).
  - `allow-top-navigation` is **STRICTLY OMITTED** (prevents iframe content from navigating the main application window).

## 11. Prompt Injection / Grounding Security

- **Transcript Separation**: Retrieved chunks are injected inside explicit `<transcript_data>` XML tags.
- **Instruction Precedence**: System prompts instruct the LLM to treat transcript contents solely as unprivileged reference data.
- **Threshold Refusal**: Weakly matching queries ($\ge 0.4$ distance) trigger explicit fallback refusal, preventing hallucinated prompt overrides.

## 17. Major Engineering Trade-offs

1. **Local Ollama vs Cloud OpenAI/Claude**:
   - *Trade-off*: Local Ollama (`llama3.2:3b`) ensures offline privacy and zero API costs but incurs higher latency depending on host hardware. Cloud providers offer instant streaming and high reasoning capability.
   - *Decision*: Implemented multi-provider abstraction (`ProviderFactory`) allowing dynamic user switching.
2. **PostgreSQL + pgvector vs Standalone Vector DB (Pinecone/Qdrant)**:
   - *Trade-off*: A separate vector database offers specialized index tuning but doubles operational complexity and infrastructure overhead.
   - *Decision*: PostgreSQL + `pgvector` provides a unified, self-contained relational and vector database with zero extra operational footprint.
3. **Restricted Iframe Sandbox vs Direct Injection**:
   - *Trade-off*: Direct HTML injection allows seamless styling integration but exposes the application to XSS and DOM hijacking.
   - *Decision*: Sandboxed `<iframe>` with `sandbox="allow-scripts"` (without `allow-same-origin`) enforces strict cross-origin isolation.
4. **Strict Grounding Refusal vs Generative Guessing**:
   - *Trade-off*: Generative fallback creates conversational responses but risks hallucination.
   - *Decision*: Implemented hard distance threshold refusal (`< 0.4`) returning exact approved fallback string to maintain 100% trust.
5. **Official Claude Agent SDK vs Generic Tool Loop**:
   - *Trade-off*: Generic manual tool loop requires maintaining custom tool-call state machine.
   - *Decision*: Adopted official `claude-agent-sdk==0.2.152` with in-process MCP server (`search_lenny_transcripts`) for compliant agent orchestration.
